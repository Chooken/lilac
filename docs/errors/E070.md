# E070: Lilac IR verification failure

The lowered IR broke a structural rule. This is never the user's mistake
directly: well-typed sources lower to verifiable IR, so `E070` points at
a compiler bug (or a hand-edited `.lir` snapshot). Report it with the
source file attached.

Checked rules:

- header present with a supported `lilac_ir` version;
- no two functions share a name (rejects a residual mangle collision or a
  user/prelude clash);
- every `%place`, `&reg`, `@func`, `#type`, `$label`, `!const` resolves;
- registers are single-static-assignment within a block (defined once,
  used after definition);
- every block ends in exactly one terminator and all branch targets exist;
- `call` arity matches the callee's `in`/`out` counts (direct calls);
- `field` indices are in bounds and match the layout's name and type;
- `copy` operands agree: two reference places are compatible under opaque
  pointers (`ref X` → `ref Y`), but a reference/value mix or two distinct
  value types is rejected;
- arithmetic widths match (`i.*` and `f.*` only on `#bit8/16/32/64/Native`);
- every `out` place is assigned at least once in its function;
- `branch.if` never tests a constant register (fold constant branches
  first);
- `panic` names a declared `!const`.

```text
error[E070]: branch to unknown block `$nope` in `@main`
  --> main.lilac:4:5
   |
 4 |     if x {
   |     ^^ invalid IR here
```
