# E020: duplicate definition

Two definitions share one name in one scope. Signatures must stay unique, so
the second definition is the error and the first binding wins.

Bad:

```lilac
get: function () result: @bit32 {
    result = 0x1
}

get: function () result: @bit32 {
    result = 0x2
}
```

```text
error[E020]: duplicate definition of `get`
  --> main.lilac:5:1
   |
 5 | get: function () result: @bit32 {
   | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
   = redefined here
  --> main.lilac:1:1
   |
 1 | get: function () result: @bit32 {
   | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ first defined here
```

Good (rename one of them):

```lilac
get_one: function () result: @bit32 {
    result = 0x1
}

get_two: function () result: @bit32 {
    result = 0x2
}
```

The same rule covers duplicate `@conversion` pairs (`FAILS_conversion.lilac`)
and duplicate structure members. Hooks are unit-global and overload by signature:
distinct signatures may share a hook name anywhere in the unit — top level or
structure member — while the same hook name with the same qualified signature
reports `E020`. An operator's hook (`@add` to `@greater_than_or_equal`,
`@negate`, `@eql`) is known by its operand types alone: overloads whose
parameters differ only in `ref`, or whose outs differ, are `E020`, since
the operator could not choose between them.

Two `test` blocks of one namespace with the same name are `E020` too:
`lilac test` reports each by its name, so give each test of a namespace
its own. Tests in different namespaces may share a name.
